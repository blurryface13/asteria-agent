# RAG 评估方法论与面试说明

> 这份文档说明简历上"性能评估"那条背后:每个指标**衡量什么**、我们代码**实际怎么测的**、以及面试被追问时**怎么完整回答**。所有数字可在 `outputs/full_kb_rag_eval/` 报告里复现。

---

## 一、一句话全景

我们对 RAG 系统做了**两类评估**,回答两个不同的问题:

| 类别 | 回答的问题 | 指标 | 衡量对象 |
|---|---|---|---|
| **检索评估** | "有没有把对的资料找回来?" | **Hit Rate@10 (Recall)** | 检索器 |
| **生成评估** | "答案是不是老实基于找回的资料?" | **Faithfulness / Answer Relevancy** | 生成器(LLM) |

一句话:**Hit Rate 管"找得准不准",Ragas 管"答得实不实"**。两者合起来才是一条完整 RAG 链路的质量。

## 二、评估语料与 Golden Test Set

- **语料**:336 篇论文 / 25,832 chunk 的联合知识库
  - 174 篇物理信道数字水印(我的研究领域,来自 Zotero)
  - 147 篇通用 CV/AI(充当**跨领域干扰项**,让检索指标更有说服力)
  - 15 篇 CS 论文(来自 Modular RAG 参考项目)
- **Golden Test Set(90 条)**:每条是一个 `(问题, 期望命中的论文)` 对
  - 构造方式:从语料里采样一个信息密集的 chunk,让 LLM(DeepSeek)**反向生成**"这个 chunk 能回答的研究问题",该 chunk 所属论文即为期望答案
  - 这是**回归测试集**——每次改检索/重排,重跑这 90 条就能量化"变好还是变坏"

### 2.1 前置基础:两种检索是怎么"找"资料的

要看懂下面那条偏差,先得分清两种检索的**匹配方式**——这也是整个混合检索的地基:

| | **词法检索 (BM25)** | **语义检索 (Dense / bge-m3)** |
|---|---|---|
| 匹配什么 | **字面词是否重合**(同一个词有没有同时出现在问题和文档里) | **意思是否接近**(把句子变成向量,算方向夹角) |
| 认得出同义词吗 | ❌ 认不出。"汽车" 和 "轿车" 在它眼里是两个无关的词 | ✅ 认得出。"汽车"和"轿车"的向量离得近 |
| 什么时候强 | 问题里有**精确术语/专有名词/型号**("BM25""ViT""qwen3-rerank") | 问题是**换了说法的口语**("那个把图片切成小块的模型") |
| 一句话 | 认**字**,不认**意** | 认**意**,不认**字** |

- **BM25** 本质是"关键词重合度打分":问题和文档共享的关键词越多、越稀有,分越高。它完全不理解含义,纯看词面。
- **Dense(bge-m3)** 是"语义相似度":先用 embedding 模型把问题和文档各自压成一个向量(一串数字),两个向量方向越接近,就认为越相关。它能跨越"换了个说法"的鸿沟。

**混合检索(我们用的)= 两者都跑一遍再融合**,就是为了取长补短:精确术语靠 BM25 兜底,换了说法靠 Dense 兜底。

### 2.2 那条偏差到底在说什么

现在回头看这句:**"自动生成的问题会复用原文的术语,天然偏向词法匹配(BM25)"**——拆开讲:

- 我们的 Golden 问题是**从某个 chunk 反向生成**的("这段文字能回答什么问题")。LLM 生成问题时,会**大量沿用这段原文里的原词**。
- 于是这个问题和它的目标文档,**字面上高度重合**——而"字面重合"正是 BM25 的最强项。
- 结果:**BM25 在这种自动评估集上会显得格外强**(尤其 Hit@1),因为评估集"恰好"喂到了它的强项。

**打个比方**:考试题是照着课本某一页原话出的填空题,那"死记硬背原文"的同学(BM25)会考得特别好;但真实工作中用户不会照着原文提问,他们会用自己的话("我想找那个讲图像分块当 token 的模型"),这时候就得靠"理解意思"的同学(Dense/语义检索)。

**所以这条偏差的完整意思是**:我的自动评估集在无意中偏袒了 BM25,高估了它的真实表现;真实用户的口语化提问会更依赖语义检索。

**面试话术**(体现你懂评估的局限):
> "我的 Golden Set 是 LLM 从原文反向生成的,问题会复用原文术语,所以对 BM25(词法匹配)偏有利——它的 Hit@1 被高估了。真实用户的问法更口语化、会换说法,更依赖语义检索。**我清楚这个偏差,所以不单看某一路的分,而是看混合融合后的整体召回,并保留了人工抽查来校准。**" —— 能主动说出评估集的局限,比数字本身更能体现工程素养。

## 三、检索评估:Hit Rate@10

**定义**:一条 query 的检索结果 top-10 里,只要**期望论文**出现(按 chunk 所属文档去重后),就算命中(hit=1),否则 0。90 条取平均就是 Hit Rate@10。它等价于 **文档级 Recall@10**。

**我们实际测了四路**(这是关键——不是只测最终结果,而是拆开每一级看贡献):

```
dense (bge-m3 向量) ─┐
                     ├─ RRF 融合(k=60) ─→ qwen3-rerank
sparse (BM25 词法) ──┘
```

| 检索档位 | Hit Rate@10 | 说明 |
|---|---|---|
| dense 单路 | 0.933 | 纯语义 |
| sparse 单路 | 0.922 | 纯词法(BM25) |
| RRF 融合 | 0.922 | 两路排名融合 |
| **+ rerank** | **0.978** | 最终档位,精排后最高 |

**结论话术**:"混合检索 + 重排把 Hit Rate@10 做到 97.8%,rerank 相比融合前提升了约 6 个点,说明精排确实修正了粗排的顺序。"

## 四、生成评估:Ragas 是什么、怎么算的

**Ragas** 是一个 RAG 专用评估框架。它的特点是**无需人工标注参考答案**(no-reference)——用一个 LLM 当裁判,按固定规则给答案打分。我们用 **qwen-plus** 当裁判。

### 4.1 Faithfulness(忠实度)—— 核心指标

**衡量什么**:答案里的每个论断,有多少能在**检索回来的原文**里找到支撑。**它只管"有没有出处",不管"对不对"。**

**算法(这是面试高频追问点,要能讲出步骤)**:
1. 把生成的答案**拆解成若干原子论断**(claims)
2. 对每个论断,让裁判 LLM 判断:这条能不能从检索到的上下文里推出(NLI 蕴含判断)
3. `Faithfulness = 被支撑的论断数 / 总论断数`

**举例**:答案有 4 句话,3 句能在检索到的段落里找到依据,1 句是模型自己加的 → faithfulness = 0.75。

### 4.2 Answer Relevancy(答案相关性)

**衡量什么**:答案是否**切题**(答非所问会低分)。算法:让 LLM 从答案**反推**它像是在回答什么问题,再算这些反推问题与原始 query 的语义相似度。只需要 `(query, answer)`,不需要上下文。

## 五、我们的实际部署行为(代码层面发生了什么)

面试官问"你这个评估到底跑了什么",完整链路是:

```
对 30 条 Golden 样本,每条:
  1. bridge.trace(query, top_k=5)           # 走完整混合检索,取 rerank 后 top-5 段落
  2. qwen_answer(query, contexts)           # qwen-plus 基于这 5 段生成答案
  3. bridge.ragas_score(query, answer,      # qwen-plus 当裁判,拆论断→逐条判蕴含
        contexts, ["faithfulness"])
  → 得到该样本的 faithfulness
30 条取平均 = 最终 Faithfulness
```

**技术栈落点**(每一环用什么):

| 环节 | 用什么 | 在哪 |
|---|---|---|
| 向量检索 | bge-m3(本地 Ollama)+ pgvector / Chroma | `knowledge_hub/retrieval/dense.py` |
| 词法检索 | BM25(rank_bm25)| `retrieval/sparse.py` |
| 融合 | RRF, k=60 | `retrieval/fusion.py` |
| 重排 | qwen3-rerank | modular RAG 桥接 |
| 生成 | qwen-plus | `scripts/formal_full_kb_ragas_eval.py:qwen_answer` |
| 裁判 | qwen-plus(DashScope)| `backend/knowledge/modular_rag.py:ragas_score` |
| 评估编排 | 自研脚本 | `scripts/formal_full_kb_ragas_eval.py` |
| 可视化 | 前端 Dashboard | `frontend/.../rag-workspace/page.tsx` |

**一个诚实的工程决策**(值得主动讲):Ragas 0.4 有个遗留的 langchain-vertexai 导入,和项目主体的 langchain 版本冲突。我没有降级 langchain(会连累主 app),而是给那个我们根本不用的导入打了个 **shim**,让 Ragas 在不破坏主环境的前提下跑起来。—— 这体现了"依赖冲突时的隔离思维"。

## 六、Faithfulness 为什么不是满分?(最重要的追问)

初版 Faithfulness = 0.867,分布是**双峰**的:30 个样本里 23 个满分 1.0(中位数=1.0),7 个离群拉低了平均。

**低分的根因不是幻觉,是"参数知识泄漏"**:
- 例:问"ViT 把 16×16 图块当 token 吗" → 答案正确,但检索到的段落里没有这句原文,模型用**自己的参数知识**答的 → faithfulness 判 0(它只认"有没有出处",不认"对不对")。
- 例:检索没召回到某子问题的精确支撑段 → 即使答案对,也低分。

**所以 Faithfulness 和检索质量是耦合的**:检索漏了,生成再准 faithfulness 也低。

**我做过一组消融实验想提升它,结果得到一个反直觉但很有价值的结论**(这段本身就是极好的面试谈资):
- 我原以为"给生成端更多上下文(top-5 → top-8)+ 收紧 prompt"能提升 faithfulness。
- **实测反而降了(0.867 → 0.780)**。原因:rank 6-8 的段落相关性偏低,模型把它们也揉进答案,裁判判这些论断"支撑不足"。
- **结论:上下文的精度比数量更重要**——喂给生成端的段落不是越多越好,低相关段落会稀释 grounding。这条规律对任何 RAG 系统都成立。

**最终采用的是原始配置(top-5)下的 Faithfulness = 0.867**——这是个诚实、可复现的数字。相比一个刻意调到 0.95+ 的"漂亮数字",0.867 + 能讲清楚"低分是参数知识泄漏而非幻觉""上下文精度 > 数量"这两个洞察,在面试里更有分量。

## 七、面试问答速查(可能被问的 + 怎么答)

**Q: Faithfulness 和 Accuracy 有什么区别?**
A: Accuracy 管答案对不对,Faithfulness 管答案有没有落在检索到的资料里。一个正确但没出处的答案,Accuracy 高、Faithfulness 低——对 RAG 系统我们更在意后者,因为可溯源、防幻觉是 RAG 的核心价值。

**Q: Ragas 不需要标准答案,那它靠什么判分?**
A: 靠 LLM 当裁判 + 固定的拆解规则。Faithfulness 是"拆论断→逐条判上下文蕴含",不依赖人工标注的 golden answer,所以能规模化跑。代价是裁判 LLM 本身有噪声,所以我看的是多样本平均而非单条。

**Q: 你的评估集才 90 条 / 30 样本,够吗?**
A: 对我这个"实验室内部知识库"的规模够用,而且我特意加了 147 篇跨领域干扰项来提高区分度。我也清楚 Golden Set 是 LLM 自动生成的、存在术语复用偏差,所以只当回归测试的相对基线,不当绝对真值——改了检索能量化对比就达到目的了。

**Q: RRF 的 k 为什么取 60?**
A: RRF 公式 `1/(k+rank)`,k 控制高排名的权重衰减。k=60 是原论文推荐值,削弱单一检索器头部的绝对主导,让两路都能贡献。我没有过度调它,因为评估集偏小,调 k 容易过拟合到这批 query。

**Q: 你怎么保证生成的答案忠实?**
A: 两层。生成端 prompt 约束"只依据检索段落作答";评估端用 Ragas Faithfulness 量化。而且我分析过低分样本——发现主要是**参数知识泄漏**(答案正确但不在检索段落里)而非幻觉;还做过消融实验,发现盲目加大上下文反而降 faithfulness,得出"上下文精度 > 数量"的结论。最终报告的是原始配置下诚实的 0.867(中位数 1.0)。
