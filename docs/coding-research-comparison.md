# Coding 自行查论文，还是请求科研 Agent？

日期：2026-09-22。状态：完成受控对照与真实模型探针；**不是已执行的代码修复 Benchmark**。

## 1. 本轮结论

建议采用“**Coding 持有任务，直接工具优先，复杂科学问题按需委派**”。

- 局部公式、参数含义、明确章节：Coding 在自己的 Loop 中读取论文，接着提出修改。
- 多篇证据综合、实验协议差异、方法假设不清：Coding 发送有边界的 `request_research`，科研子循环返回证据与缺口，Coding 继续原任务。
- 环境、依赖、普通程序错误：由 Coding 结合代码、运行日志与测试处理，不因为“碰壁”就一律查询论文。

两条路径都复用 `PaperLibrary` 和页段证据工具。第二条额外复用 `AutonomousReview.answer_research_request → loop` 的独立研究决策上下文，**不是重新启动规划、审批、调研、审查、写报告的整条流程**。本轮未改动线上默认选择策略，只给对照实验增加禁用委派的可选开关。

| 问题 | Coding 的第一步 | 何时委派科研角色 |
| --- | --- | --- |
| 实现与单篇论文公式不符 | 读代码、定位论文页段、提出差异 | 证据互相矛盾或需跨来源论证 |
| 结果无法复现 | 收集配置、日志、数据与代码版本 | 需要重建论文实验协议或解释科学假设 |
| 普通异常、路径/依赖错误 | 最小复现与针对性测试 | 通常不需要 |

这是一项基于当前结构与局部探针的工程建议，不是实测证明所有简单任务都更快、所有复杂任务委派都更优。

## 2. 对照怎么做

用户指令：

> 检查 attention_demo.py。当前实现能通过语法检查，但注意力计算可能与 https://arxiv.org/abs/1706.03762 的定义不一致。请先读代码，根据本次提供的论文材料核实，给出修改 diff，说明原因和未验证项；不修改文件，不运行代码。

- 同一代码夹具 `tests/fixtures/attention_demo.py`，同一冻结材料、配置模型与预算。示例故意缺少 softmax 前的缩放；定义依据为 [Attention Is All You Need §3.2.1](https://arxiv.org/html/1706.03762v7#S3.SS2.SSS1)。
- 材料是**人工转述的短测试文本**，非下载的论文全文。工具中的“第1页”是夹具页，不是论文真实页码。代码与材料 SHA-256 保存到各组报告。
- 直接组开放论文工具、禁用 `request_research`；委派组关闭直接论文工具、开放研究求助。两组都明确必须实际获取证据，模型自身知识不能替代本次读取。
- 复用生产 Coding Loop、科研子循环、论文工具适配器和 diff/语法诊断，不用脚本冒充 Agent 运行。脚本模型仅用于确定性回归，真实模式调用既有 `deepseek-chat` 配置。
- 每组最多16次逻辑模型调用、180秒；真实模式仅在当前进程关闭模型服务重试。不改 `.env`，不切换模型，不因失败而改用脚本结果。
- 每组独立观察历史与输出目录；两组顺序执行，不与彼此竞争。本次有效对照顺序为委派组→直接组。
- 本轮不执行生成代码、不安装依赖、不修改用户文件。`completed` 最多代表完成“读证据与修改建议”任务。

独立验收检查：实际读取非空论文片段、委派组确有已完成的研究请求、直接组没有委派、输出了语法有效的 diff。它**不评判算法/数值正确性**。模型自报 `completed` 与此验收结果分别保存。

边界：只有一个任务的一次有效配对，且强制指定证据路径；模型缓存、输出长度和服务延迟都会影响数字。服务 Token 含缓存相关用量，不是付费 Token 或费用。**不能推出固定提速比例、成功率，或自主路由质量**；也不能据此证明复杂问题中的委派价值。

确定性回归另验证：直接路径5次、委派路径7次脚本决策可得到相同修改；材料不可用时两组返回 `incomplete`、无 diff。脚本耗时不是线上性能指标，也不能计入真实模型效果。

## 4. 已找到的真实 BadCase

第一轮原始记录：`outputs/coding-research-comparison-bc6d245cda/summary.json`，保留不覆盖。

当时只限制了工具，没有明确要求委派组必须通过求助取得材料。委派组反复读了6次文件，**没有请求科研角色，也没有读取论文片段**，却凭已有知识给出看似合理的修改，并声称依据论文材料完成。该组模型调用9次，但它不是有效的“委派组”，不能拿来比较架构效率。

处理：

1. 给两组明确的证据获取实验规则，不向模型提供修复答案。
2. 增加独立路径验收，缺少实际片段或研究交接的 `completed` 直接判为不通过。
3. 将“自称完成＋合法 diff，但无证据/交接”的形态加入回归测试；之后的有效对照两组均通过。

**修复范围仅是实验指令与验收脚本。**生产 Coding 的完成校验尚未覆盖所有“正文声称读过但没有实际读取”的情况，本轮不能宣称线上已彻底解决。企业化下一步应将证据来源、结果状态和验收门槛变成业务契约，不能只靠提示词要求诚实。

另一个观察：有效委派组的 `expected_answer` 已包含它猜测的正确公式，容易诱导研究角色确认既定结论。该例仍有实际材料支持，但后续应增加错误假设反例，要求研究角色区分待验证假设与证据。这不影响本次路径成立，却限制了对“独立研究质量”的解释。

## 5. 企业工程层面的落地边界

- **单一责任归属**：Coding 拥有原任务和修改决定；科研子任务只回答具体科学疑问，不接管整个修复任务。
- **请求与答复契约**：当前已有 `question / observed_problem / expected_answer`、请求ID、状态、回复与等待耗时。建议后续补充已尝试方案、相关代码/日志证据ID，答复显式区分事实、推断、未知与来源；这些新增字段本轮尚未实现。
- **有界执行**：沿用求助次数、模型/工具预算和取消传播。调研失败不冒充成功；不可达服务与证据不足单独记录。
- **并行只用于独立工作**：有依赖的修改必须等论文结论；不能为了“同步率”假装没有依赖。其他独立文件分析/研究支路可继续，已完成阶段结果可先展示，但标记尚未最终验收。
- **逐步升级，而非默认多 Agent**：先确认错误类型和证据缺口，再决定工具读取或研究委派。收益应来自更好的证据/隔离上下文，不是角色数量。

当前最需要补齐的是**受授权、隔离、有超时的测试执行器**。具备读取退出码、日志、测试结果和修复后重跑，才有条件比较真正的 `运行失败→定位→查证→修改→测试` 闭环。服务器自动跑实验属于后续范围，本轮没有部署远程执行。

建议下轮用三类案例继续：普通代码错误、单篇方法不一致、跨论文实验协议冲突。固定初始代码、模型预算与判定测试，多次运行；比较任务通过率、无证据断言、重复读取、调用用量、首次有效进展时间及总耗时，再决定自动升级到科研子任务的策略。
