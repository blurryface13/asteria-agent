# 科研 Base 验收、协作诊断与通用任务扩展

2026-09-25。状态：本轮方案已确认，复杂综述真实验收进行中；下文不代表功能已全部实现。

## 1. 已确认的架构与优先级

1. 先验收现有 Anthropic 2025 Research 风格 Base：Lead 决策与派工、同类 Search Subagent 的独立工具循环和互补 aspect、Run Memory、Writer 与 CitationAgent。完整边界见 [架构对齐记录](anthropic-research-alignment.md)。本轮不重构外层意图路由，不增加新的主管层。
2. 复杂综述目标：正文实际引用至少 10 篇不同学术文献，按问题综合而非逐篇堆摘要，保留方法适用条件与分歧，输出可读报告及 PDF。篇幅为软目标。来源数量是本测试用户要求，不是所有研究任务的固定终止门槛。
3. 从真实轨迹和产物定位一个主要问题，记录动机、复现、根因、局部修复、回归与验收。没有改善则如实记录，不能提前制造面试故事或提升数字。
4. 随后推进 AstaBench 适配与能力扩展；用户更偏好通用领域 search/report（例如金融行业研究），优先于扩大 Coding。报告研究不等于投资建议或交易执行，不要求新增领域 Agent 群。

## 2. Coding 调用边界（后续设计，非本轮重构）

- 科研复合任务中 Lead 直接调用 Coding Agent；Search 和 Coding 是同级执行者，Search 不直接启动 Coding。
- Coding 在独立工作区内自行完成读代码、修改、执行、测试、调试的工具循环，Lead 不逐步指挥每次 Shell 调用。
- Coding 的局部论文问题可自己调用阅读/RAG 工具；需要独立调研或改变整体方案时向 Lead 请求，由 Lead 决定派发 Search。
- 独立 Coding 入口可以继续存在，不强迫所有任务经过科研 Lead。
- 工作副本隔离不等于执行安全沙箱；修改权限、进程资源和网络授权另行约束。

## 3. 8·13 文档：动机、观察与结论

一手来源：Anthropic Frontier Red Team，2026-08-13，[Patterns and problems in emerging multiagent systems](https://www.anthropic.com/research/multiagent-systems)。

**动机**：个体 Agent 能力提升不自动保证群体协作；共享资源、分散信息与不同目标会放大行为偏差。文章用实验暴露机制问题，而非交付通用架构。

**观察**：相对独立任务容易并行，强依赖的软件协作困难；仅指定角色或 CEO 没有明显改善其游戏开发实验。相近模型和上下文容易产生同质行动；群体可能漏传独有证据、过早形成共识，或轻信不可靠信息；互相冲突的目标可能引发对抗。

**结论**：更强的个体智能/对齐不足以自然产生协调；交互环境与机制仍需专门设计。不能由此推出 Leader 无效、并行无效，或照搬人类组织即可解决问题。

### 7.4 本轮已定位的局部性能问题：并行研究争用 Embedding

实际基线中，三路研究同时下载原文并调用在线 RAG。前几次 retrieve 的实测总耗时为 65.07、192.71、211.81 秒；之后一项暖语料查询仍耗时 68.74 秒。该总耗时包含排队、Embedding 与检索，不能当成纯模型推理时间。

代码定位：`HybridContextCompressor._embed_texts` 在整个语料的分批编码循环外持有全局信号量。默认并发为 1，前方大语料持续占用资源，短请求和缓存命中查询也必须等待。这是资源层队头阻塞，不是 Lead 没有并行，也不是必须新增 Agent 才能解决。

局部修改：信号量改为**每批获取/释放**，保持批大小和提供方并发上限；所有分块仍参与相同检索排序，不裁剪语料、不关闭 RAG、不增加模型调用。已在旧代码上重现测试失败：短请求排在大语料所有批次之后；修改后通过，验证短请求在下一批之前获得执行机会、向量顺序不变、并发仍为 1、取消释放资源。正在执行的基线 worker 已加载旧实现，未热更新或混入修改。

与 8·13 的关系是**本项目的工程类比**：多 Agent 的并行能力不能消除共享资源竞争，需要明确协调机制。原文没有提出本项目的批级信号量实现；此修改也不解决模型同质化、信息遗漏等所有问题。公平调度不减少总编码工作量，可能让大请求稍晚完成；不预先宣称总体任务耗时下降。后续需单独验证修改后的真实运行。

### 7.5 基线终止：基础设施错误被放大为重复补研

Run `e6b2bc9fd37d4d09b14f6969db153ee6` 最终 **failed**，没有报告。记录执行 669.85 秒、94 次模型调用、27 篇已读资料、6 个子 Agent；供应商记录输入 1,994,485 / 输出 46,030 Token，包含缓存使用，费用未知。这些是失败成本，不是成功案例。

完整因果链：

1. PDF 提取的证据含 `U+0000`。检索工具的 JSON 字符串观察可以保存，但解码后的嵌套证据在 `finish` 事件写 PostgreSQL JSONB 时触发 `UntranslatableCharacterError`。
2. 该基础设施异常进入普通工具错误观察，子 Agent 连续重试 `finish`，最终耗尽行动轮次。轨迹共记录 6 次失败的 `finish` 和 1 次失败的 `delegate`。
3. Lead 收到未完成结果，又派发补研。不是资料没有读到，也不能直接归因于子 Agent 的知识能力不足；跨角色交接状态让基础设施失败扩散成了额外推理与检索。
4. Lead 最终明确收尾，但写作 Skill 选择连续两次同时选择互斥的内容角色，触发 `Choose at most one primary writing skill`，任务在写作前退出。

局部修复：

- **事件存储边界**：将值中的 NUL 替换为可见 `U+FFFD`，保留字符位置、整段证据及原始文件；不修改调用方对象，也不修改普通换行/制表/数学字符，字面量 `\\u0000` 保持原样。持久化事件附 `_storage_normalization` 计数，日志不输出原文。协议字段名不静默改写，以免键冲突。真实 PostgreSQL 隔离 schema 已验证子 Agent 交付事件可写入及读回。
- **写作选择契约**：模型使用一个标量 `content_skill` 加可选 `guidance_skills`，只允许一个主写作角色；保持用户固定 Skill 和格式选择不被覆盖。内部仍转换为原 `WritingSelection`，不改前端/用户请求格式。不靠放宽校验或任意丢弃第二个写作角色“假通过”。
- **观察恢复**：验收脚本支持 `--resume outputs/acceptance_<id>`，只允许恢复本仓库专用测试账号的历史任务；核验账号归属后重置临时凭据，继续原 Run、从最后事件序号补拉，不重复提交，不保存密码或令牌。

与 8·13 的联系是局部工程映射：协作系统必须正确传递成果与失败原因，不能仅依赖角色人设。本次未实证复现其游戏实验、群体从众或对抗行为，也没有证明 Ledger 能解决这些问题。

### 7.7 复测过程中发现的诊断缺口（补丁尚未影响当前 Run）

复测第一批三路结束时间分别为 271.002、705.838、724.018 秒，前两路分别回传 8、12 条 findings，第三路以 incomplete 回传且没有 findings。第三路保留的最后两条观察均为 `Invalid action JSON/schema`，但旧 observe_error 丢弃了 Pydantic 具体异常，因此**无法事后断言是输出截断、字段超限还是格式错误**。Lead 随后读取其完整产物并针对记忆/评测补研，同时仍有补充代表性方法的任务，需结合最终质量判断哪些补研必要。

新增小修复：给模型返回字段路径、错误类型与约束说明，并留下 `decision_error` 事件；不记录原始模型响应、input 或 context 字段。回归验证错误 `gaps` 类型能够在下一次决策修复，保持原行动上限，不增加隐藏重试、不放宽权限。当前 worker 已在运行，补丁未热更新；该 Run 不计作此项补丁的真实验证。

初步体验结论：复杂任务的主要耗时已不只是模型推理。本次读取了多篇几十页原文，首次建立本地向量索引占据较长时间；批级公平调度不减少总编码量，不能从单路提早返回推断总体加速。后续可通过持久化内容哈希缓存减少跨 Run 重复编码，但需验证模型/分块版本失效与用户隔离后再实施，本轮未擅自切换 RAG 模式。
